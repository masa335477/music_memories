
## アプリ名： Music Memories

## 1. サービス概要
このアプリは、各々の好きな音楽への情熱を他人に共有するための音楽特化型SNSである。まだ自分の知らない楽曲に出会える場所を目指す。

## 2. このアイデアはどこから生まれたか
音楽を聴くときに、自分が好きな楽曲を友達や恋人・職場の同僚にも紹介できるようにし、その楽曲の良さを分かち合いたいと思って作ろうとした。

### きっかけとなった体験・感情
音楽を聴いている中で、ただ自分が聴いて終わりではなく、その曲に対する思いを残すことができたらと思ったから。また、他人が自分の好きな曲に対して、コメントを残して分かち合うことができたならと思っている。

### なぜそれが「気になった」のか
- 自分の性格
自分はもともと音楽を聴くことが大好きである。毎日家でもスマホで音楽を聴くし、通勤する時も車でCDをかけるのが当たり前である。
- 過去の経験
自分の好きな楽曲を他人にもっと聴いてもらえるきっかけを作ることができたならと思った。
音楽鑑賞アプリ（SpotifyやApple Music等）では、楽曲を聴くことに特化しているため、コメントを残すことはどうしても重視していない印象があった。
そこで、音楽を検索し、その楽曲について感想や思い出を投稿・共有できるサービスを作りたいと考えた。

## 3. 課題の整理

### 表に見えている困りごと
既存SNSでは、音楽以外の話題も表示されること。

### 本当に解決したい課題
音楽以外の話題に埋もれず、音楽についての投稿を探せる、音楽に特化したサービスを作りたい。
→これは、高い熱量を持った音楽の感想を探す時に、それが雑多な話題に埋もれてしまうことで、結果的に時間がかかってしまうからである。

他人の好みを尊重しながら、自分の好みも大切にしたい。
→どんなに各々の好きな楽曲を語っても、反応や共感を得ることは難しい。音楽の好みや聴き方は人それぞれであり、日常の話題が中心となる既存のSNSでは、お互いの趣味がぴったり重なるタイミングを見つけるのは少し難しいであろう。いきなり知らないアーティストの楽曲を勧められた際、どうしても「この曲自分に合うかわからない」という不安は誰にでもある自然なことである。

## 4. 想定ユーザーについて

### どんなユーザーを想定しているか
- アルバム全体を通して音楽を楽しむユーザー
アルバムを通して聴くことは、楽曲の構成や楽曲と楽曲同士とのつながりから得るドラマ性を味わうことができるといったメリットがある。また、同じ楽曲でも、その楽曲が収録されているアルバムを通して聴くことにより、単体で聴く時とは違う印象を持つと考える。本アプリは、そんな楽曲単体で聴く人より、アルバム全体で聴いたときの感情を共有したいという人にお勧めしている。

- もっと好みを深めたい・広げたいユーザー

### 実際に使われる可能性について(需要・存在意義)
- 需要
Xをはじめとする総合SNSでは、好きな音楽やコンサートについてテキストで熱弁することができる。しかし、既存の総合SNS（特にX）は日常の雑多な話題も多く表示されるため、「音楽の話題だけを見たい・盛り上がりたい」「熱量の高いレポだけを読みたい」という音楽ファンの需要を完全に満たしているとは言えない。また、音楽の投稿が他の話題に埋もれてしまう点もある。

- 存在意義
本サービスでは、楽曲・アルバムに対する感想や思い出など、音楽に関する投稿に特化する。
雑多な話題をタイムラインから排除するため、ユーザーは本当に興味のある音楽の話題だけに集中できる。他のユーザーの熱量のあるコメントを通じて音楽体験を味わうことにより、新しい音楽と出会える。

### 最初に優先するユーザー
最初に優先するユーザーは、他の人の感想や音楽への思いを手がかりに、次に聴く音楽を見つけたい人とする。

- 利用例

    開くきっかけ： 普段聴いている音楽とは異なる作品にも興味があるが、どの楽曲・アルバムを聴けばよいか分からない。

    最初の操作： Music Memoriesを開き、他のユーザーが投稿したアルバムの感想を閲覧する。

    得られる価値： 楽曲やアルバムの評価だけでなく、投稿者が感じた曲そのものの魅力やアルバム全体の魅力、好きになった理由を知ることで、自分では気づかなかった聴きどころを発見できる。

    再訪するタイミング： 紹介された楽曲・アルバムを実際に聴いた後、別の作品についても感想を探したいときや、自分の音楽の好みを広げたいときに再び利用する。

### ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)
普段聴いている音楽とは異なる作品にも興味があるものの、どの楽曲・アルバムを聴けばよいか分からないユーザーがいるとする。

そのユーザーは、単なる評価やおすすめ曲・アルバムだけでなく、他の人がどのような理由で楽曲やアルバムを好きになったのかを知りたいと考え、Music Memoriesにアクセスする。

投稿一覧から興味を持ったアルバムの感想を読み、作品全体の世界観や曲順、投稿者が感じた魅力を知ることで、これまで知らなかったアルバムに興味を持つ。

その後、実際にアルバムを聴いてみたり、別の作品についても感想を探したりするために再び利用する。

将来的には、自分自身もアルバムの感想や音楽への思いを投稿し、他のユーザーと共有することで、音楽の楽しみ方を広げていくことを目指す。

### それでも自分が作りたい理由
既存サービスと投稿・交流の基本機能は重なる部分は多い。そこで、上記の機能に加え、以下の機能を加えたいと考えている。
①アルバムの投稿機能
本サービスでは「アルバム単位での投稿」も軸に据える（Melologとの比較）。楽曲単体では語り尽くせない「楽曲構成」「曲順の妙」「曲と曲の繋ぎ」「作品全体のストーリーや空気感、メッセージ性」まで語り合うことができる場にしたいと考えている。また、「1曲がアルバムの中でどういった役割を果たしているか」を語ることの楽しさも味わえるようにしたい。そのために、「作品全体」を語れる専用投稿フォーマットを設ける（Chooningとの比較）。

- 作品全体」を語れる専用投稿フォーマットの項目例
・アルバム全体の印象・世界観
・特に印象に残った楽曲とその理由
・曲順や曲同士のつながりについて感じたこと
・そのアルバムを好きな理由や思い出

②ランキング形式での投稿（全アプリとの比較）
一つの投稿（スレッド）に対して、複数の楽曲やアルバムをランキング形式でストック・共有できる機能を実装する。複数の楽曲・アルバムを一つのテーマのもとにランキング形式でまとめ、それぞれの選出理由まで語れるようにする。
例えば、「人生を変えた楽曲3選」や「初めて聴いた時に衝撃を受けた曲ベスト5」といった、ユーザー独自のテーマに沿ったセレクトを可能にする。また、単発の曲紹介ではなく、順位やテーマという「文脈（コンテキスト）」を持たせることで、投稿者は選曲のこだわりをより深く表現できる。これにより、見る側にとっても「短時間でもテーマや選出理由を手がかりに、新しい音楽を発見できる」というメリットが生まれる。

この①と②の機能を使うことにより、新しい楽曲に出会うことが容易になると考える。

③グラデーション・レコメンド機能の実装（全アプリとの比較）
本アプリでは、「自分の大好きな楽曲・アルバム」を大切に語れる場所をベースにしつつ、相手のこれまでの好みにそっと寄り添う『グラデーション・レコメンド』などの仕組みを取り入れる。 聴き手の心の準備やペースに配慮した動線を作ることで、無理なく自然に「それなら、ちょっと聴いてみようかな」と思える、心地よい共感の輪を広げられる場所を目指す。

例えば、
1. ユーザーが好きなアーティストに「サカナクション」を登録
2. 「サカナクションが好きな人がよく聴くバンド」
3. 「同じく日本語詞とメロディを重視するバンド」
4. 「少し方向性の違うバンド」
5. 「あなたの好みから少し離れているが、共通点のあるアーティスト」

というように、既知 → 近い → 少し違う → 未知という段階を作る。

### Musicboardとの差別化について
本アプリは、楽曲やアルバムについて投稿・評価・記録することができるという点で、Musicboardと共通している。そこで、本アプリでは単に音楽を評価・記録するのではなく、「その楽曲・アルバムを好きになったきっかけ」「自分にとってどのような楽曲なのか」等といったユーザー自身の音楽体験を共有することを重視する。
また、アルバム全体について語れる投稿や、テーマに沿って複数の楽曲・アルバムを選出するランキング投稿などを実装する。これにより、単一作品の評価だけでは表現しきれない、ユーザー自身の音楽観や思い出を共有できるようにする。

### Chooningとの差別化について
Chooningは、楽曲の感想やライブの思い出を記録・共有できるサービスである。本サービスも音楽について投稿・交流できる点では共通するが、単に音楽について語る場を提供するだけでなく、ユーザー自身の音楽観を表現・蓄積し、そこから新しい音楽との出会いにつなげることを重視する。

具体的には、複数の楽曲やアルバムをテーマ・順位・選出理由とともに紹介できるランキング投稿機能や、アルバム全体の構成・曲順・世界観について語れる投稿機能を実装する。これにより、個々の作品の感想だけでなく、ユーザーがどのような音楽を好み、何に魅力を感じているのかを表現できるようにする。さらに、投稿やお気に入りの音楽を蓄積し、自分の音楽の好みや、音楽と人生の思い出を振り返れる仕組みを目指す。

このように、本サービスでは、音楽について投稿すること自体を目的とするのではなく、「自分の好きな音楽を深く知る」「他者の好きな音楽から新しい視点を得る」「その出会いを通じて自分の音楽の世界を広げる」という一連の体験を提供することを目指す。

### 既存の手段では不足する理由
音楽レビューサービスやSNSでも、アルバムの感想や音楽にまつわる思い出を共有することはできる。しかし、自由記述を中心とした投稿では、投稿者が何を伝えたいかによって情報の内容や構成が異なり、読み手が作品全体の魅力や投稿者の音楽に対する考え方を把握しにくい場合がある。

Music Memoriesでは、楽曲単体だけでなく、アルバム全体について語るための専用投稿フォーマットを用意する。これにより、以下の内容を伝えやすくする。

    作品全体の印象： アルバム全体の雰囲気や世界観、伝わってくるメッセージ

    曲順や曲同士のつながり： 曲の配置や曲間の流れによって生まれる魅力

    印象に残った楽曲とその役割： 特に好きな楽曲だけでなく、アルバム全体の中でその楽曲がどのような役割を果たしていると感じたか

    投稿者がその作品を好きな理由： 個人的な体験や感情も含め、なぜそのアルバムに惹かれるのか

これらを通じて、投稿者は自分の感想を整理して伝えやすくなり、読み手は単なる評価やおすすめ曲だけでは分からない作品の魅力を発見しやすくなる。

当然、既存サービスの自由記述でも同様の感想を書くことは可能であり、Music Memoriesだけがアルバムの魅力を語れるわけではない。本サービスを選ぶ最大の理由は、アルバム全体を語るための視点が用意されており、他の人の音楽の楽しみ方を知ることから、新しい作品への興味につなげられることにある。


### 差別化を「体験価値」で表現すると
①1曲単位では語りきれない、アルバムならではのストーリー性を含めた熱量を語れる場所。
②人の好きという感情を通じて音楽を知り、語り、さらに新しい音楽へ出会おう。

## 6. このサービスで提供したい価値

### ユーザーの変化
他のユーザーが音楽を好きな理由や、作品全体についての感想を知ることで、これまで知らなかった音楽に興味を持ち、自分の音楽の楽しみ方を広げられる。また、将来的には、自分が好きな音楽への思いや体験を投稿することで、他のユーザーの新しい音楽との出会いにもつながる。

### 価値を一文で表すと
「好き」という感情から、まだ知らない音楽と出会える場所。

### MVPで検証する仮説
他の人がアルバムを好きな理由を読むことで、未聴の作品を聴いてみたいと思えるか。

### 検証に必要な機能
① Spotify Web APIを利用したアルバム検索と基本情報の取得
② アルバム全体の印象や好きな理由などを記載できる投稿機能
③ 投稿一覧・投稿詳細の閲覧機能

### 価値が伝わったと判断する基準
利用者が投稿を読んだ後、次のような行動や感想を示すかを確認する。
    ① まだ聴いたことのないアルバムに興味を持ち、実際に聴いてみたいと感じる。

    ② 投稿を読む前には知らなかった、アルバムの魅力や聴きどころを発見する。

    ③特に、どのような感想や情報がアルバムへの興味につながったかを具体的に説明できる。

### 初期段階での検証方法
初期段階では投稿数やコメント数が少ないことを想定し、開発者自身が複数のアルバムについて投稿を用意する。そのうえで、少人数の利用者に投稿を閲覧してもらい、興味を持った作品や、聴いてみたいと思った理由を聞き取る。

分析機能を新たに実装するのではなく、利用後の質問や簡単な聞き取りを通じて、仮説が支持されるかを確認する。検証結果をもとに、投稿フォーマットや表示内容を改善する。

②： 日替わり候補の選定、他ユーザーからの推薦、表示
③： 順位、テーマ、選出理由、並び替え
④： 説明画面、案内、操作フロー
⑤： 登録・削除、プロフィールへの保存
⑥： 段階的な推薦、候補の並び替え、推薦理由
⑦： 投稿履歴の時系列表示、振り返り画面
⑧： 表示サイズの切り替え、拡大・縮小、設定の保存

### Spotify Web APIでの実装と自ら実装の違い
Spotify Web APIは、楽曲・アルバム・アーティストの検索および基本情報の取得に利用する。取得した音楽情報を投稿やプロフィールに紐付けるための処理、投稿・交流・タグ・ランキングなどのSNS機能は、RailsとPostgreSQLを用いて独自に実装する。

おすすめ機能では、Spotify Web APIから取得した音楽情報を推薦対象の表示に利用し、ユーザーが登録した好きなアーティスト、投稿に付与されたタグ、投稿への反応などを自サービスのデータベースに蓄積して、独自の推薦ロジックで候補を選定する。

## 8. このアプリの懸念点とその対策

### 懸念点
ChooningやMusicboard、Record Clubなどの先行類似サービスが存在するため、機能やコンセプトが重複し、新規ユーザーに見向いてもらえない、または既存サービスから移行してもらえない懸念がある。

### 対策
- 3つの「機能・体験的アプローチ」によるポジショニングの明確化
既存サービスには、楽曲の記録やアルバムの評価を中心としたサービスが存在する。一方、本サービスでは、「評価すること」よりも、「なぜその音楽が好きなのかを語ること」「好みを他者と共有すること」に重点を置く。

1. 投稿単位の差別化（アルバム・ランキング特化）：
1曲単位ではなく、「アルバムの曲順や流れ」や「テーマ別ランキング（ベスト3など）」に特化。単なる記録ではなく、音楽ファンの「1曲では語りきれない熱量」を解放する場にする。

2. 心理的ハードルを下げる「グラデーション・レコメンド」：
ユーザーの好みや、他のユーザーが登録・紹介した音楽を手がかりに、既に知っている音楽から、好みに近い音楽、少し異なる音楽へと段階的に出会える仕組みを実装する。

「自分の投稿 ➔ 相手の好みの提示 ➔ いいね ➔ 次のおすすめの段階的開示」という、ユーザーの好みや反応を手がかりに、ユーザーの警戒心（知らない・苦手な曲への抵抗）を汲み取った優しいレコメンド動線を独自実装する。

ユーザーにとって馴染みのない音楽をいきなり提示するのではなく、その楽曲の推薦理由や共通点を示すことにより、ユーザーが自分のペースで新しい音楽に興味を持てる体験を目指す。

3. 優しさに配慮したUI/UX（未知の音楽を押し付けられないUX）：
ジャケット写真をあえて小さくする配慮など、「押し付けない、押し付けられない、自分のペースで音楽を楽しめる安心感」を徹底することで、既存の激しいSNSや批評サイトに疲れたユーザーの受け皿となるだろう。

- 3.における位置づけ
中心となる独自性： アルバム投稿、ランキング投稿、段階的な音楽発見

補助的なUX： 推薦理由を表示する、興味のないおすすめをスキップできる、ジャケットの表示サイズを変更できる

## 10. 技術スタック(手段としての技術)

### 使う技術（予定）
言語：Ruby(3.4.11)
フレームワーク：Ruby on Rails(8.1.4)
フロントエンド：TypeScript, Hotwire(Turbo/Stimulus)
データベース：PostgreSQL
開発環境：Docker
デプロイ先：Render
外部API：Spotify Web API

- それぞれの役割
Rails： データ処理、認証、投稿・コメント・いいねの保存

Hotwire（Turbo）： ページ遷移や部分更新、サーバーからの画面更新

Stimulus＋TypeScript： Spotify検索結果の選択や画面上の操作、ランキング投稿における楽曲・アルバムの並び替えなど、ユーザーの操作に応じた画面の動的な処理に利用

- Ruby・Ruby on Railsのバージョン選定理由
Rubyについては、Ruby 3.4系の機能を利用しながら、不具合修正が反映されたバージョンで開発を進めることを目的とする。

Ruby on Railsについては、Rails 8.1系の機能を活用し、ユーザー登録、投稿、コメント、いいねなどの機能を効率的に実装することを目的とする。

なお、バージョンの新しさだけを優先するのではなく、使用するGemとの互換性やデプロイ環境での動作も考慮して選定した。

- HotwireおよびTypeScriptを採用する理由：
本アプリでは、投稿・コメント・いいねなどの基本的な処理をRails側で実装し、Hotwireを利用して画面の部分更新を行う。これにより、Railsを中心とした構成を維持しつつ、必要な動的UIを実現する。

TypeScriptはStimulusコントローラー上で利用し、Spotify APIの検索結果を扱う画面操作や、ランキング投稿における楽曲やアルバムの並び替え等、ユーザーの操作に応じて画面を動的に変化させる機能に活用する予定である。

- データベース・開発環境
Docker上でPostgreSQLを動作させ、環境構築の再現性を高める。本番環境ではホスティングサービス上のPostgreSQLを利用し、PCやスマートフォンなど複数の端末から同じアカウント・投稿データにアクセスできる構成とする。

- Spotify APIの利用方針と制約
Spotify Web APIの開発モードでは、アプリ所有者のSpotify Premium加入が必要であり、Spotify認証を利用するユーザー数にも制限がある。また、楽曲検索の取得件数にも上限があるため、検索結果のページネーションやAPIエラーへの対応を考慮して設計する。

初期段階では、Spotify Web APIを楽曲・アルバム・アーティストの検索と基本情報の取得に利用し、アプリ内での音源再生・試聴機能には依存しない方針とする。取得した音楽情報やジャケット画像を表示する際は、Spotifyの公式ポリシーに従い、必要な帰属表示とSpotifyへのリンクを設ける。

また、開発モードの制約を踏まえ、ポートフォリオとしての動作確認を優先し、将来的に利用者を拡大する場合は、Spotifyの最新の利用条件を確認したうえで対応方針を検討する。
